# pdman v0.8.x release notes

v0.8.x focuses on the read-only records query layer and the records doctor contract. It turns existing runtime history into compact, agent-readable records without introducing a database, repairing metadata, mutating queue state, or changing downloader behavior.

## Release theme

The v0.8 line makes records inspection explicit and script-friendly:

- `pdman records list` exposes compact task summaries from runtime history.
- `pdman records metadata` derives cache metadata locators by URL, target path, or run id.
- `pdman records show` inspects one `run_id + task_id` record with diagnostics and debug suggestions.
- `pdman records schema` documents records surfaces for scripts and agents.
- `pdman records doctor` provides a read-only records health check with stable JSON, JSONL, readable, and schema contracts.

## YAML schema v2 foundation

v0.8.17 resumes the original v0.8 roadmap item for YAML schema v2 while preserving all legacy task input formats.

Schema v2 adds:

```text
version: 2
defaults
groups
group-scoped tasks
```

Task resolution precedence is stable:

```text
task > group > defaults
```

`pdman -i tasks.yaml --list-groups` lists available schema v2 groups and exits without downloading. `pdman -i tasks.yaml --group <name> --dry-run` resolves tasks and prints them without starting downloads. `pdman -i tasks.yaml --group <name>` loads only that group into the normal download flow.

Only `file_name`, `dir_path`, `md5`, and `log_path` are mapped into current download tasks in v0.8.17. Additional schema v2 fields are preserved in `TaskInput.options` for dry-run visibility and future contract expansion, but they do not yet change per-task downloader behavior.

v0.8.18 applies the same schema v2 group resolution to `pdman queue add`:

```text
pdman queue add -i tasks.yaml --list-groups
pdman queue add -i tasks.yaml --group <name> --dry-run
pdman queue add -i tasks.yaml --group <name> --dry-run --json
pdman queue add -i tasks.yaml --group <name>
```

`queue add --dry-run --json` reports `dry_run=true`, `would_add`, `count`, and preview records. It does not write `queue.jsonl`. Queue record schema stays at v1 and does not persist `TaskInput.options`; schema v2 fields such as `retry`, `headers`, or `max_connections` remain future contract inputs rather than queue record fields.

v0.8.19 adds task input contract inspection:

```text
pdman input schema
pdman input schema --json
```

The schema output describes legacy plain/JSON/YAML inputs, YAML schema v2 structural fields, task/group/defaults precedence, mapped fields, preserved option fields, and non-goals. It does not read task files, start downloads, write queue records, or change per-task downloader behavior.

v0.8.20 adds stable validation reason codes for schema v2 and dry-run diagnostics. Human dry-run errors use `[code] message`; queue JSON errors use this shape:

```json
{"error": {"code": "schema_v2_defaults_not_mapping", "message": "schema v2 defaults must be a mapping", "field": "defaults"}}
```

Current stable codes include `schema_v2_missing_version`, `schema_v2_defaults_not_mapping`, `schema_v2_groups_not_mapping`, `schema_v2_group_not_mapping`, `schema_v2_tasks_not_list`, `schema_v2_group_tasks_not_list`, `task_mapping_url_missing`, `schema_v2_group_not_found`, and `group_requires_schema_v2`.

v0.8.21 aligns the main download entrypoint with queue dry-run diagnostics:

```text
pdman -i tasks.yaml --group <name> --dry-run --json
pdman -i tasks.yaml --list-groups --json
```

Main dry-run JSON output reports `dry_run=true`, `count`, `group`, and resolved `tasks`. Resolved tasks include mapped fields and preserve schema v2 option fields under `options`; the command still exits before creating a `Manager` or starting downloads. Main dry-run JSON errors reuse the same `{error: {code, message, field}}` shape as queue add.

## Records query surfaces

The records layer reads existing runtime history and emits compact views for users, scripts, and agents. It does not read complete `resume-metadata.json` or `dynamic-ranges.json` content.

Stable v0.8 records commands:

```text
pdman records list
pdman records metadata
pdman records show --run-id <run-id> --task-id <task-id>
pdman records doctor
pdman records schema
```

All records commands are read-only. They do not start downloads, recover downloads, repair metadata, clear tmp state, mutate queue files, or migrate history.

## Metadata locator contract

`pdman records metadata` and `pdman records show` expose metadata locators, not metadata contents. Locator entries report only path and availability diagnostics:

```text
path
exists
source
status
reason
```

Current locator keys are:

```text
resume
dynamic_ranges
```

If a record lacks a URL, metadata location is unavailable and reported as such. If metadata paths are derived but files are absent, status is `missing` with reason `file_missing`.

The current cache layout remains an implementation detail:

```text
cache_root/metadata/<url-hash>/
```

This is a cache layout, not a permanent database schema or public record identifier.

## Single record inspection

`pdman records show --run-id <run-id> --task-id <task-id>` returns one task record summary plus compact diagnostics:

- Basic task identity and status fields.
- Compact error fields where available.
- `resume_rejection`, `header_probe`, and `network_error` payloads.
- Metadata locator diagnostics.
- Structured `suggested_debug` actions.
- Compatible shell-oriented `suggested_commands`.

Debug suggestions are suggestions only. Records show does not execute debug commands and does not validate or repair metadata.

## Records doctor contract

`pdman records doctor` is the final v0.8 health-check surface for records data quality. It is read-only and does not repair or migrate anything.

Stable doctor issue codes currently include:

| Code | Meaning |
| --- | --- |
| `invalid_status` | Record status is missing or not supported by the records schema. |
| `run_id_missing` | Record cannot be traced to a stable run id. |
| `task_id_missing` | Record cannot be addressed by task-scoped records workflows. |
| `url_missing` | Metadata locator and debug suggestions cannot be derived from the record. |

Each doctor issue contains:

```text
code
severity
message
impact
suggested_action
run_id
task_id
url
target_path
```

Doctor JSON output is the full report:

```text
schema_version
status
records_checked
issue_count
total_issue_count
filters
warning_count
error_count
status_counts
metadata_state_counts
issue_groups
issues
```

Doctor JSONL output is an issue stream only: one `doctor_issue` per line. It intentionally does not contain summary fields or `issue_groups`.

Readable doctor output is human-oriented but has a stable section order:

```text
summary
status_counts
metadata_state_counts
issue_groups
issues
```

`pdman records schema --surface doctor --json` exposes the same output-mode boundary through `output_contract`, so agents can choose `readable`, `json`, or `jsonl` without probing live doctor output first.

## Stable script-facing surfaces

Scripts and agents should prefer JSON or JSONL output from these records commands:

- `pdman records list --json`
- `pdman records list --jsonl`
- `pdman records metadata --json`
- `pdman records metadata --jsonl`
- `pdman records show --json`
- `pdman records doctor --json`
- `pdman records doctor --jsonl`
- `pdman records schema --json`
- `pdman records schema --surface doctor --json`

Human-readable output remains useful for users and release diagnostics, but scripts should not depend on free-form human text except where explicitly documented as a readable contract summary.

## Explicit non-goals in v0.8.x

v0.8.x intentionally does not do the following:

- Add a database or index engine.
- Define a permanent records database schema.
- Embed full resume or dynamic metadata contents into records output.
- Validate or repair metadata files.
- Repair history records.
- Migrate legacy history or metadata.
- Enable dynamic recovery.
- Execute debug commands automatically.
- Mutate queue schema or queue records.
- Change downloader scheduling, retry, range allocation, or network behavior as part of records work.
- Perform Python version compatibility sweeps.

## Release readiness status

The v0.8 records doctor sub-stage is considered closed at v0.8.15. v0.8.16 adds release notes and boundary documentation only.

Recommended release-readiness checks before tagging v0.8.x:

```text
PYTHONPATH=src python -m pytest -q tests/test_records.py tests/test_cli_records.py
PYTHONPATH=src python -m pytest -q tests/test_output.py tests/test_history.py tests/test_queue.py tests/test_cli_history.py tests/test_manager.py
```

Full-suite execution may include local HTTP/download tests and should be run in an environment where those tests are known not to hang. If a full-suite command times out, verify whether it left a pytest process behind before rerunning.

## Transition after v0.8

v0.8 leaves pdman with a stable read-only records layer and records doctor contract. Future work should be planned as separate version themes rather than appended to records doctor.

Recommended future themes:

1. Python version compatibility sweep for the declared support range.
2. Database or indexed records query layer, if needed, as a new explicit schema project.
3. Metadata validation or repair, kept separate from read-only records inspection.
4. Dynamic recovery only after metadata lookup and validation boundaries are stable.
