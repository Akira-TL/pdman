# pdman v0.6.x release notes

v0.6.x focuses on resume diagnostics, metadata contracts, and agent/script-readable inspection. It does not enable dynamic recovery. The main outcome is that pdman can now explain why temporary download state was accepted, rejected, or only available for inspection.

## Release theme

The v0.6 line turns resume state from implicit temporary files into documented diagnostics:

- `resume-metadata.json` becomes the strict v2 recovery contract.
- Static `--continue` validates metadata before reusing partial files.
- Dynamic downloads can emit metadata for inspection, but do not recover from it yet.
- Resume rejection reasons become stable code-bearing diagnostics.
- History and run detail gain JSON outputs for scripts and agents.
- `pdman debug resume` exposes read-only metadata inspection.

## Recovery contract

`resume-metadata.json` is the strict v2 recovery contract. It records identity and layout information used to decide whether existing temporary files are safe to reuse:

- `schema_version`, currently `2`.
- `kind`, currently `resume`.
- `mode`, either `static` or `dynamic`.
- `url`, `filename`, and `target_path`.
- `file_size`, `etag`, and `last_modified`.
- `segments`, including index, byte range, partial path, expected size, existing size, and state.

Static resume validates URL, target path, file size, etag, last-modified, segment layout, and partial sizes before reusing tmp state. If validation rejects v2 metadata, pdman discards stale tmp state and restarts instead of falling back to legacy `.pdm`.

Changing static chunk options such as `-x` or `-k` does not by itself invalidate existing v2 metadata. pdman follows the segment layout stored in metadata.

## Dynamic boundary

Dynamic downloads can emit `resume-metadata.json` and `dynamic-ranges.json`, but dynamic recovery is still not enabled in v0.6.x.

The boundary is intentional:

- `resume-metadata.json` is the recovery contract.
- `dynamic-ranges.json` is debug metadata for allocator inspection.
- `pdman debug ranges` reads dynamic range debug metadata.
- `pdman debug resume` reads resume metadata.
- The two surfaces must not be treated as interchangeable.

## Resume rejection diagnostics

Resume rejection messages use the stable format:

```text
Resume rejected [<code>]: <message>
```

Scripts and agents should use the structured fields where possible:

- Runtime history fields: `resume_rejection_code`, `resume_rejection_reason`.
- JSON payload: `resume_rejection.present`, `resume_rejection.code`, `resume_rejection.reason`.

A resume rejection is diagnostic. It does not automatically mean the task failed. A task can reject old tmp state, restart from scratch, and still finish successfully.

## Script and agent reading paths

Use the narrowest surface that answers the question:

| Question | Recommended command |
| --- | --- |
| What happened in recent tasks? | `pdman history --json` |
| Process each history record independently | `pdman history --jsonl` |
| Inspect one run and its tasks | `pdman run <run_id> --json` |
| Inspect one resume metadata file | `pdman debug resume --metadata <path> --json` |
| Find latest resume metadata under tmp/cache roots | `pdman debug resume --latest --json` |
| Filter resume segments by state | `pdman debug resume --metadata <path> --state partial --jsonl` |
| Inspect dynamic allocator debug ranges | `pdman debug ranges --json` |

Human-readable output remains useful for users, but scripts should prefer JSON/JSONL and avoid parsing human text.

## Stable output surfaces

The v0.6 JSON/JSONL surfaces intended for scripts and agents are:

- `pdman history --json`
- `pdman history --jsonl`
- `pdman run <run_id> --json`
- `pdman debug resume --metadata <path> --json`
- `pdman debug resume --metadata <path> --jsonl`
- `pdman debug resume --latest --json`
- `pdman debug resume --latest --jsonl`
- `pdman debug ranges --json`
- `pdman debug ranges --jsonl`

The full stable resume diagnostics field list is documented in `docs/resume-diagnostics.md`.

## Explicit non-goals in v0.6.x

v0.6.x does not do the following:

- Enable dynamic recovery.
- Repair corrupted partial files.
- Migrate legacy `.pdm` files into v2 metadata.
- Expose full resume metadata through history or run JSON.
- Change exit code only because resume metadata was rejected.
- Treat `dynamic-ranges.json` as a recovery contract.

## Transition to v0.7

v0.6.x leaves pdman with a stable diagnostics foundation. v0.7 can now focus on a larger behavior change without also redefining diagnostics.

Recommended v0.7 themes:

1. Network request strategy and HEAD-to-GET fallback.
2. Request behavior tuning and diagnostics around headers/status handling.
3. Dynamic recovery planning only after request behavior is stable.

If v0.7 chooses dynamic recovery, it should be treated as a high-risk feature and should reuse the v0.6 diagnostics contract rather than replacing it.
