# pdman v0.7.x release notes

v0.7.x focuses on network request strategy, network failure taxonomy, range failure taxonomy, metadata storage hygiene, and debug latest observability. It does not enable dynamic recovery, does not introduce a database, and does not expand queue schema.

## Release theme

The v0.7 line turns network and metadata behavior into explicit, test-backed contracts:

- Header inspection uses a controlled HEAD-to-GET-probe strategy.
- Header probe fallback is exposed as structured diagnostics.
- Network failures are classified into stable phases and kinds.
- Static and dynamic range failures are distinguished at task level.
- New metadata writes move out of task tmp and into cache metadata.
- `debug --latest` is cache/search-root bounded and exposes readable diagnostics.

## Request probe contract

Header inspection follows this strategy:

1. Try `HEAD` first.
2. Accept only `200` or `206` as successful HEAD status.
3. Fallback to GET probe for common HEAD-incompatible status codes: `403`, `404`, `405`, and `501`.
4. Fallback to GET probe for HEAD connection-class failures.
5. GET probe uses `Range: bytes=0-0` and is only used for header inspection.
6. Retryable HEAD statuses such as 5xx, `408`, `425`, and `429` do not fallback to GET probe.

The fallback reason codes are stable:

| Reason code | Meaning |
| --- | --- |
| `head_http_403` | HEAD returned 403. |
| `head_http_404` | HEAD returned 404. |
| `head_http_405` | HEAD returned 405. |
| `head_http_501` | HEAD returned 501. |
| `head_connection_error` | HEAD failed before a usable response. |

When fallback is used, human-readable output shows the fallback. JSON output exposes a `header_probe` object where applicable. Queue records intentionally do not copy this diagnostic.

## Network failure taxonomy

Task-level network failures use stable phases and kinds for scripts and agents.

Stable phases:

| Phase | Meaning |
| --- | --- |
| `connect` | Connection setup failed before usable header information. |
| `header_head` | HEAD header inspection failed. |
| `header_get_probe` | GET probe header inspection failed. |
| `range_static` | Static chunk/range download failed. |
| `range_dynamic` | Dynamic range download failed. |

Stable kinds:

| Kind | Meaning |
| --- | --- |
| `connection_timeout` | Connection or request timed out. |
| `connection_failed` | Connection failed for a non-timeout reason. |
| `http_status` | HTTP status rejection. |
| `range_incomplete` | Range body or static aggregate size was incomplete. |
| `range_response` | Range response or Content-Range validation failed. |

This taxonomy is task-level. It does not copy every range-level error into `TaskResult` or queue records.

## Metadata storage hygiene

v0.7.6 changes the default metadata write location for new runs:

- New runs do not write `.pdm` to task tmp.
- New runs do not write `resume-metadata.json` to task tmp.
- New runs do not write `dynamic-ranges.json` to task tmp.
- Task tmp keeps chunk and partial files only.
- New `resume-metadata.json` and `dynamic-ranges.json` are written under the cache metadata directory.

Current cache layout:

```text
cache_root/
  metadata/
    <url-hash>/
      resume-metadata.json
      dynamic-ranges.json
```

`<url-hash>` is currently derived from the URL hash prefix. This is a cache layout, not a database schema.

Compatibility remains:

- Existing legacy tmp `resume-metadata.json` can still be read by `--continue`.
- Existing legacy `.pdm` can still be used as the final fallback.
- New runs do not create those tmp metadata files.

## Cache metadata lifecycle

Fallback order for resume metadata is:

1. Cache `resume-metadata.json`.
2. Legacy tmp `resume-metadata.json`.
3. Legacy `.pdm`.

If cache metadata is stale or invalid, pdman ignores it and does not clear tmp partials. If legacy tmp v2 metadata is present but invalid, pdman clears tmp and does not fallback to `.pdm`. If stale cache metadata is ignored and a later legacy tmp metadata path succeeds, stale cache rejection diagnostics are cleared.

`pdman debug resume --latest` and `pdman debug ranges --latest` search only the cache root by default. With `--cache-dir`, they search only that cache dir. With `--search-root`, the specified roots become the strict search boundary. System tmp is not searched by default.

Latest discovery skips invalid metadata candidates and selects the newest valid candidate.

## Debug latest readable diagnostics

Readable `debug --latest` output shows latest search diagnostics:

```text
Latest search:
  root: /path/to/cache
  valid: 1
  skipped_invalid: 2
```

Missing latest output shows searched roots:

```text
No resume metadata found.
Searched:
  /path/to/cache
```

`debug ranges --latest` uses the same format.

These diagnostics are readable-only in v0.7.x. Automation should prefer `--json` or `--jsonl`. JSON and JSONL payloads do not include `latest_search`, `search_roots`, `valid_count`, or `skipped_invalid_count`.

## Stable script-facing surfaces

The v0.7 line extends but does not replace the v0.6 script-facing diagnostics surfaces:

- `pdman history --json`
- `pdman history --jsonl`
- `pdman run <run_id> --json`
- `pdman debug resume --metadata <path> --json`
- `pdman debug resume --metadata <path> --jsonl`
- `pdman debug resume --latest --json`
- `pdman debug resume --latest --jsonl`
- `pdman debug ranges --json`
- `pdman debug ranges --jsonl`

Human-readable output is allowed to improve across v0.7.x. Scripts should not parse it.

## Explicit non-goals in v0.7.x

v0.7.x does not do the following:

- Enable dynamic recovery.
- Add a database or indexed records query layer.
- Add `--from-run` metadata lookup.
- Add metadata locator fields to history or run JSON.
- Expand queue schema with header probe or network taxonomy payloads.
- Embed full metadata content into history or run records.
- Reintroduce tmp metadata writes for new runs.
- Change retry/backoff semantics as part of the taxonomy work.

## Migration and operational notes

- Users with old tmp directories can still inspect old metadata with explicit paths or `--search-root`.
- Default `debug --latest` no longer scans system tmp.
- New metadata should be expected under the cache metadata directory.
- A task can reject stale cache metadata and still successfully recover through legacy tmp metadata.
- Queue records remain intentionally smaller than task/run/history diagnostics.

## Transition after v0.7

v0.7 leaves pdman with stable request diagnostics, network taxonomy, and cache metadata hygiene. Future records/database work should be planned as a separate version line rather than being retrofitted into the v0.7 metadata cache layout.

Recommended future themes:

1. Records or database-backed query layer for task/run metadata lookup.
2. Agent-readable metadata lookup by URL, target path, or run id.
3. Dynamic recovery only after metadata lookup and request behavior are stable.
