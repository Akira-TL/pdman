# pdman v0.9.x release notes

v0.9.x focuses on output modes and agent adaptation. It turns pdman's existing human output and scattered JSON/JSONL command surfaces into a planned top-level output contract for humans, shell scripts, CI systems, and LLM agents.

## Release theme

The v0.9 line will make output selection explicit and script-friendly:

- `rich` remains the interactive TTY-oriented output mode.
- `plain` becomes the non-TTY/log-oriented output mode.
- `json` is reserved for final machine-readable command summaries.
- `jsonl` is reserved for incremental machine-readable event streams.
- Existing command-specific `--json` and `--jsonl` surfaces remain compatible while the top-level output contract is introduced.

## Version timeline

| Version | Summary |
| --- | --- |
| v0.9.0 | Adds the output mode contract foundation with stable mode names and TTY default resolution. |
| v0.9.1 | Adds the main download `--output rich|plain|json|jsonl` parser option and passes the resolved mode to `Manager`. |
| v0.9.2 | Adds the first renderer boundary: Rich output keeps Rich progress, while non-Rich modes use a no-op progress sink. |
| v0.9.3 | Adds plain lifecycle output for run start, terminal task results, and final summary while keeping structured modes quiet. |
| v0.9.4 | Adds `--output json` final download summary payload and moves structured-mode console/log output away from stdout. |

## Output mode contract foundation

v0.9.0 introduces the stable output mode names:

```text
rich
plain
json
jsonl
```

The initial resolver contract is:

```text
explicit selection > TTY default > non-TTY default
```

Default behavior:

| Context | Effective mode |
| --- | --- |
| TTY, no explicit mode | `rich` |
| Non-TTY, no explicit mode | `plain` |
| Explicit mode provided | selected mode |

Structured output modes are:

```text
json
jsonl
```

These modes must keep stdout machine-readable once they are connected to command execution. Human progress, Rich rendering, and incidental log text must not be mixed into stdout for structured modes.

## Planned download output modes

The planned top-level CLI shape is:

```text
pdman --output rich <url>
pdman --output plain <url>
pdman --output json <url>
pdman --output jsonl <url>
```

The intended semantics are:

| Mode | Intended use | Shape |
| --- | --- | --- |
| `rich` | Interactive users | Rich progress and human summary |
| `plain` | Logs, nohup, CI text logs | ANSI-free lifecycle lines and summary |
| `json` | Scripts and CI summary parsing | One final JSON object |
| `jsonl` | Agents and long-running automation | One JSON event object per line |

## Planned JSONL event stream

The planned event stream should be incremental, stable, and free of ANSI sequences.

Example event kinds:

```text
run_started
task_started
progress
retry
skipped
completed
failed
run_finished
```

Every event should include at least:

```text
schema_version
event
run_id
```

Task-scoped events should also include:

```text
task_id
url
status or lifecycle-specific fields
reason or error where applicable
```

Progress events must be throttled. They should respect the existing progress summary interval rather than emitting one event per chunk write.

## Compatibility with existing structured surfaces

Before v0.9, pdman already has command-specific structured output for records, history, queue, debug, and input inspection. v0.9 keeps those surfaces compatible.

Existing flags such as `--json` and `--jsonl` remain valid for their current commands. The top-level `--output` contract should be added without breaking those command-specific surfaces.

## Explicit non-goals in v0.9.x

v0.9.x intentionally does not do the following:

- Change downloader scheduling, retry, range allocation, or network behavior.
- Enable dynamic recovery.
- Repair metadata or history records.
- Add a database or index engine.
- Expand queue record schema.
- Map YAML schema v2 option fields into per-task downloader behavior.
- Redefine existing records, queue, debug, history, or input JSON payloads.
- Perform a broad Python version compatibility sweep.

## Main download parser foundation

v0.9.1 adds the main download parser option:

```text
--output rich|plain|json|jsonl
```

This option is currently scoped to the main download entrypoint. Existing subcommands continue to use their command-specific `--json` and `--jsonl` flags. The parsed mode is resolved with the same TTY default contract and stored on `Manager.output_mode` for later renderer integration.

v0.9.1 does not yet change rendering. `rich`, `plain`, `json`, and `jsonl` currently select the future output contract state, but the existing Rich-based main download behavior remains in place until dedicated renderer work lands.

## Renderer boundary foundation

v0.9.2 introduces the first renderer boundary:

```text
RichOutputRenderer
PlainOutputRenderer
NoOpProgress
```

`rich` mode continues to create the existing Rich progress object. `plain`, `json`, and `jsonl` currently use the plain renderer's no-op progress sink. This gives Downloader a progress-compatible object while preventing non-Rich modes from starting interactive Rich progress rendering.

The no-op progress sink intentionally accepts the same methods used by current downloader code: `add_task`, `update`, `remove_task`, `stop_task`, and context-manager enter/exit.

v0.9.2 still does not emit plain lifecycle lines, JSON final summaries, or JSONL events. It only separates the progress rendering boundary so those later stages can be added without rewriting downloader scheduling.

## Plain lifecycle output

v0.9.3 adds low-frequency plain lifecycle output for `--output plain`:

```text
Run started: <run-id>
Task completed: <name> task_id=<task-id> reason=<reason>
Summary:
  completed: <n>
  skipped: <n>
  failed: <n>
```

This output is intentionally terminal-event oriented. It does not emit high-frequency progress lines, so it remains suitable for CI logs, `nohup`, and redirected output.

`rich` mode keeps the existing interactive behavior and final summary. `json` and `jsonl` remain quiet for human lifecycle output until their dedicated structured contracts land.

## JSON final summary output

v0.9.4 adds `--output json` final summary output. At the end of a download run, JSON mode emits one machine-readable object to stdout:

```json
{
  "schema_version": 1,
  "kind": "download_summary",
  "run_id": "...",
  "status": "completed",
  "exit_code": 0,
  "counts": {
    "completed": 1,
    "skipped": 0,
    "failed": 0
  },
  "tasks": []
}
```

Each task item includes task identity, URL, filename, terminal status, reason fields, byte counts, and existing diagnostic payloads for resume rejection, header probe fallback, and network errors.

Structured modes now use a structured renderer boundary whose console targets stderr. This keeps stdout reserved for the final JSON object in `json` mode and for future event lines in `jsonl` mode.

`jsonl` remains quiet in v0.9.4 because the incremental event stream is a separate contract stage.

## Release readiness status

v0.9.0 is a contract foundation step only. It adds stable output mode names and default resolution tests. v0.9.1 adds the main download `--output` parser foundation. v0.9.2 adds the first renderer/progress boundary. v0.9.3 adds plain lifecycle lines. v0.9.4 adds JSON final summary output. These versions do not yet add the JSONL event stream.

Recommended checks for v0.9.4:

```text
PYTHONPATH=src python -m pytest -q tests/test_output_modes.py
PYTHONPATH=src python -m pytest -q tests/test_output.py tests/test_cli.py tests/test_manager.py
```

## Transition after v0.9.4

The next stage should add `--output jsonl` event streaming with one JSON event per line while keeping the final JSON summary contract unchanged.
